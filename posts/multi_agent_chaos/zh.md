### “智能体围炉夜话”的诱人幻觉

在多智能体演示中，最吸睛的往往是模拟软件团队：拉起五个大语言模型（LLM）扮演的角色——产品经理、架构师、前端工程师、后端工程师、QA测试，扔进一个开放聊天频道，然后敲下一行提示词：*“帮我写一个分布式键值存储系统。”*

前三分钟，终端里的景象宛若魔法。产品经理迅速输出用户故事，架构师建议采用 Raft 共识算法，工程师们热火朝天地互相致意。

然而到了第四分钟，画风开始走偏。

架构师和后端工程师陷入了无限的客套循环：
> *“关于 Raft 日志压缩的提议非常棒！我们是否也该对内存映射文件做个基准测试？”*  
> *“这个想法很独到！内存映射文件确实能优化 I/O。产品经理怎么看存储上限的问题？”*  
> *“从用户体验出发，可靠存储至关重要！我们先把边界情况梳理清楚吧。”*

到了第十二轮对话，上下文窗口有一半被互相吹捧的废话塞满，模型凭空捏造了三个根本不存在的 API，而真正能运行的代码却连一行都没写出来。这简直是以每轮 0.06 美元的成本，极其逼真地复刻了一场职场中各怀心思、只点头不落地的低效委员会例会。

把多智能体协作当成毫无约束的自由聊天室，在工程上注定走入死胡同。当智能体像人类那样东拉西扯时，不仅继承了人类团队所有的组织内耗，而且缺乏人类天然具备的现实纠偏机制。


### 多智能体系统为何频繁失控？

为什么自由交流的智能体网络总是难以收敛？根本原因在于三个结构性缺陷：

1. **跨轮次的认知漂移（Epistemic Drift）**  
   大语言模型的每一次补全本质上都是概率采样。当智能体 A 向智能体 B 传递一段自由文本解释时，智能体 B 只能基于对 A 意图的概率估算来生成回复。到了第四轮，最初的技术目标早已在类似“传话游戏”的概率迭代中严重变形。诸如“严格线程安全”或“禁止引入外部依赖”等微妙约束，彻底淹没在泛泛而谈的散文中。

2. **责任发散与终止条件缺失**  
   在点对点的扁平智能体网络里，没有任何一个模型对终态结果负责。如果智能体 A 挑了智能体 B 代码里的毛病，智能体 B 修改后又回抛给智能体 A 重新审阅。缺乏强制的外部停止准则，整个循环往往只能靠触发 Token 截断、超时或限流硬性终止。

3. **上下文二次膨胀（Quadratic Context Bloat）**  
   如果每个智能体都能看到所有其他智能体的对话全文，Token 消耗量将随着智能体数量呈二次方爆炸。更糟糕的是，上下文里充斥着大量客套话和重复摘要，直接破坏了模型原本的推理质量。


### 构建高信噪比多智能体系统的三条准则

过去两年在 Windsurf 与 Google DeepMind 开发智能体系统的经历，让我体会最深的一点是：**真正可靠的多智能体架构，长得绝不像社交网络；它们更像经典的分布式系统。**

要想把失控的智能体狂欢变成可落地的生产级流水线，需要遵循以下三条设计原则：


#### 1. 严禁自由闲聊，全面采用 RPC 强类型接口

对于智能体之间的通信而言，自由自然语言是最糟糕的序列化协议。它直接诱发了冗余、歧义和臆造范围。

子智能体之间不应该进行任何点对点的辩论。相反，应该采用**分层编排器（Hierarchical Orchestrator）**，通过严格定义的类型化 Schema 分发任务：

```python
from pydantic import BaseModel, Field

class CodeEditRequest(BaseModel):
    target_file: str
    instruction: str
    context_lines: list[int] = Field(description="相关代码行切片")

class CodeEditResult(BaseModel):
    patch: str = Field(description="统一 diff 格式补丁")
    files_modified: list[str]
    verification_passed: bool
    compiler_error: str | None = None
```

编排器不需要向执行节点询问“你怎么看”。它分配原子任务，限定输入范围，并等待一个类型确定的结构化载荷。如果执行失败，子节点只需返回标准错误码，而不是洋洋洒洒解释一段内疚的心路历程。


#### 2. 上下文完全隔离，仅共享交付产物（Artifacts）

一个常见的反模式是把智能体 A 的完整执行轨迹一股脑塞给智能体 B。这会导致智能体 B 的上下文被 A 失败的尝试、无关的工具输出以及思考草稿严重污染。

子智能体应该在**隔离的上下文分支**中独立运行。它们只接收执行具体子任务所需的最小信息，在专用沙箱里干活，最后仅回传干净的交付产物：

- 一段具体的代码补丁（diff）
- 一份独立的 Markdown 报告或产物
- 一个附带复现步骤的布尔型验证结论

编排器只审查交付物本身，而不去通读混乱的中间推理轨迹。这既保证了主控上下文的精简，也防止了上游混乱污染下游执行节点。


#### 3. 必须由确定性验证工具裁决结果

只要存在确定性的检验工具，就绝不要用大语言模型去评估另一个大语言模型的产出。

当智能体写完代码后，不要拉一个“审查智能体”去问代码写得对不对。直接调用编译器、Linter 和单元测试套件：

```bash
# 确定性的客观事实永远胜过大模型的自我感觉
pytest tests/unit -q && mypy src/ --strict
```

测试运行器的输出毫无歧义：零样本、不可贿赂、几乎不消耗 Token。要么通过测试，要么测试失败。如果一个智能体反复尝试三次仍无法修复测试报错，立刻触发熔断机制（circuit breaker），回滚沙箱环境，并将决策权交还给人类开发者。


### 返璞归真的系统演进

最抓人眼球的智能体演示，总是在描绘由单条提示词驱动、通过“群体涌现”自运转的自动化公司。

但在实际生产中，这种所谓的群体涌现，往往只涌现出了车轱辘话和飞涨的云账单。

真正能在工业界稳定产出高质量代码的智能体架构，往往出奇地传统：有向无环图（DAG）、具备确定性转移条件的状态机、隔离的沙箱工作区，以及类型严苛的 RPC 契约。

如果你希望智能体真正为你编写可用软件，别再让它们聚在数字茶水间里闲扯了。给它们清晰的职责说明、隔离的运行沙箱，以及一台无情的自动化编译器。
